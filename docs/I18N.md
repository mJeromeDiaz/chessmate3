# Langues — Don't Stay Rooky

> Chemins relatifs à `front/` (sauf mention de `api/`).

Le site est en **français** et en **anglais** (choix du 2026-10-14). Le français est la langue
**source** : tous les textes sont écrits d'abord en français ; l'anglais (et les langues à venir)
sont traduits à partir de lui.

## 1. Règles validées (2026-10-14)

- **Langue d'une première visite** : la première des langues du navigateur que le site parle
  (`fr-CA` → français) ; sinon l'**anglais**, langue par défaut.
- **Choix du joueur** : un menu « FR / EN » dans l'en-tête de la landing, un sélecteur dans le
  profil (« Préférences »). Le choix est gardé dans le navigateur (`dontstayrooky.locale`, appliqué
  avant le premier affichage) et, connecté, sur le compte (`app_user.locale`, `PUT
  /api/profile/locale`), comme le thème : le choix du compte l'emporte au chargement du profil ; un
  compte sans choix reçoit celui du navigateur.
- **Texte manquant** : une clé absente d'une langue s'affiche en français (`fallbackLocale`), sans
  avertissement dans la console.
- Ce qui vient de la base (offres de la boutique, positions d'évaluation, noms d'ouvertures et de
  thèmes) n'est pas traduit pour l'instant.
- Lots : F0 socle, F1 à F8 front par domaine, puis l'API (A1 langue côté serveur, A2 emails et
  notifications push, A3 messages, export, calendrier).

## 2. Organisation

| Élément | Emplacement |
|---|---|
| Instance, langues, `t()` hors composant, `intlLocale()`, `browserLocale()` | `src/i18n/index.js` |
| Messages | `src/i18n/<langue>/<domaine>.json` : le fichier `fr/woodpecker.json` donne les clés `woodpecker.*` |
| Langue courante (navigateur, compte, Quasar, `<html lang>`) | `src/stores/locale.js`, appliquée par `src/boot/i18n.js` |
| Sélecteurs | `components/theme/LocaleMenu.vue` (landing), `components/profile/LocaleSection.vue` (profil) |
| API | `App\Enum\Locale`, `App\Entity\User::$locale`, `App\Dto\Profile\LocaleRequest`, `ProfileController::setLocale` (migration `Version20261021090000`), `locale` dans `GET /api/profile` et l'export |

Conventions (lots F1 et suivants) :

- **Template** : `$t('domaine.cle')` (injection globale) ; une phrase qui contient un élément
  (`<b>`, un lien) passe par `<i18n-t keypath="…" tag="p" scope="global">` et un `<template
  #nom>` par élément, pour que l'ordre des mots reste libre dans chaque langue.
- **Script** d'un composant, store ou utilitaire : `import { t } from '@/i18n'`, appelé au moment
  d'afficher (dans un `computed`, une fonction), jamais figé au chargement du module.
- **Constantes de données** (liens de navigation, options, cartes des profs) : les textes
  deviennent des accesseurs (`get label() { return t('layout.nav.home') }`) ; la forme de l'objet
  ne change pas pour ceux qui le lisent.
- **Valeurs enregistrées** : un choix gardé (brouillon de session, réglage envoyé à l'API) est une
  valeur neutre (`'black'`, `'video'`, `4`), jamais un libellé ; le libellé se lit au moment
  d'afficher (`field.optionLabel(v)` dans `utils/session/catalog.js`). Les brouillons de session
  d'avant le 2026-10-14, aux libellés français, sont convertis à la lecture (`upgradeValues`).
- Tables « clé → libellé » (statuts, rayons, niveaux…) : `labelMap('domaine.groupe', [clés])`
  (`src/i18n/index.js`) rend un objet dont chaque propriété est lue dans la langue courante.
- Pluriel français (`frenchPlural`) : 0 et 1 au singulier ; les messages à deux formes s'écrivent
  `"{n} partie | {n} parties"` et s'appellent `t('cle', n)` ou `t('cle', { n }, n)`.
- Noms des jours : `Intl` (`WEEKDAYS` de `utils/session/plans.js`), pas de messages.
- Un `@` dans un message s'écrit `{'@'}` (syntaxe vue-i18n), comme `|` et `{` littéraux.
- Messages communs (boutons « Continuer », « Annuler », erreurs génériques de l'API) :
  `common.json`. Pluriels (syntaxe vue-i18n) : `"aucun puzzle | 1 puzzle
| {n} puzzles"` et `t('cle', n)`. Les messages JSON sont précompilés par
`@intlify/unplugin-vue-i18n` (`quasar.config.js`, `include: src/i18n/**/*.json` : surtout pas `index.js`, que le plugin prendrait pour un fichier de messages et refuserait).

Dates et nombres : toujours `Intl` avec `intlLocale()` (`fr-FR`, `en-GB` : jour avant le mois et
horloge sur 24 h dans les deux langues), jamais une langue écrite en dur. Les composants Quasar
(boutons des fenêtres, calendriers) suivent la langue (`quasar/lang/fr`, `en-GB`).

## 3. Traduire

1. Ajouter ou compléter `src/i18n/en/<domaine>.json` avec les mêmes clés que `fr/<domaine>.json`.
2. `npm run i18n:missing` liste, fichier par fichier, les clés à traduire (et celles qui ne
   servent plus) ; `npm run i18n:missing -- en` pour une seule langue. Code de sortie 1 tant qu'il
   en manque.

Ajouter une langue : son code dans `LOCALES`, son nom dans `LOCALE_NAMES`, sa balise `Intl` et son
paquet Quasar (`stores/locale.js`), son cas dans `App\Enum\Locale`, puis le dossier
`src/i18n/<code>/`.

## 4. Tests

- Vitest tourne en français (`tests/unit/setup.js`) : les tests attendent les textes source.
  `tests/unit/i18n.test.js` : langue du navigateur, balises `Intl`, repli sur le français.
- Playwright simule un navigateur français (`locale: 'fr-FR'`, `playwright.config.js`) ;
  `tests/e2e/profile.spec.js` change la langue dans le profil (enregistrée, `<html lang>`).
- PHPUnit : `tests/Functional/Profile/LocaleTest.php`.

## 5. L'API

> Chemins relatifs à `api/`.

- **Outil** : `symfony/translation` 7.4 (`config/packages/translation.yaml`). Messages par domaine
  dans `translations/<domaine>.<langue>.yaml` (`emails.fr.yaml`, `emails.en.yaml`…), comme le front.
- **Anglais par défaut, jamais le français** (choix du 2026-10-14) : `default_locale: en`, repli
  `en`. Les deux langues sont écrites (le français d'origine, l'anglais à relire), aucun fichier
  `.en.yaml` ne reste vide.
- **Langue d'une requête** : son en-tête `Accept-Language` parmi `enabled_locales` (`en`, `fr`),
  anglais sinon (`set_locale_from_accept_language`). Le front l'envoie à chaque appel avec la langue
  affichée (`src/services/http.js`), appels publics compris (liste d'attente, inscription) ;
  l'en-tête est autorisé par CORS.
- **Langue d'un envoi** : `App\I18n\UserLocale::of($user)` donne le choix du compte
  (`app_user.locale`), sinon la langue de la requête servie, sinon l'anglais (un worker, un cron :
  pas de requête). `of()` sans compte : un visiteur.
- **Emails** (lot A2, 2026-10-17) : `App\Mailer\EmailTemplates::compose($nom, $langue, $contexte)`
  donne un `TemplatedEmail` dont l'objet est le message `<nom>.subject` du domaine `emails` et les
  corps `templates/emails/<nom>.{html,txt}.twig`, rendus dans cette langue (`TemplatedEmail::locale()`,
  valable aussi depuis la file d'attente). Les gabarits commencent par `{% trans_default_domain
  'emails' %}` et n'écrivent plus de texte : `{{ 'mfa_code.intro'|trans }}`. Dates en paramètres
  (`%date%` en `d/m/Y`, `%time%` en `H:i`), jamais un « à » dans un format de date. Une phrase HTML
  qui contient un lien ou du gras reçoit ce morceau en paramètre, construit par le gabarit avec les
  valeurs échappées (`|e`), et s'affiche avec `|raw` ; la version texte a sa clé `_text` quand la
  phrase change (lien en dessous). Pluriels : `%count%` et `"… minute|… minutes"` (pas d'ICU :
  `intl` n'est pas garanti sur l'hébergement).
- Langue de chaque email : le compte (`UserLocale::of($user)`) pour ceux qui partent dans une
  requête (code de connexion, vérification, mot de passe, liaison, suppression) ; la
  réinitialisation, envoyée par un worker, emporte la langue de la requête dans
  `PasswordResetRequested::$locale` (le choix du compte l'emporte) ; l'adresse déjà prise écrit au
  compte qui la possède ; l'invitation, la langue enregistrée sur elle (docs/EARLY_ACCESS.md) ; les
  rappels (session, série), envoyés par le cron, le compte, anglais sans choix.
- **Push** : les deux notifications (rappel de session, série en danger) sont traduites avec leurs
  emails (`translations/notifications.<langue>.yaml`, textes partagés dans `emails`). Noms des
  modules des étapes : `translations/training.<langue>.yaml` (`module.<valeur>`).
- Les libellés envoyés au front (types de finales, plans, catégories, thèmes) restent des clés ou
  arrivent dans les deux langues : le front les traduit (choix du 2026-10-14). Fait au lot A3a
  (2026-10-17) : grades d'XP (`rank` est une clé, `gamification.ranks.*`), types de finales du
  diagnostic (`type`, `coach.endgames.*`), plans et types de position de l'évaluation (`value`,
  `tag` : `evaluation.plans.*`, `evaluation.tags.*`), évaluation du moteur écrite par le front
  depuis `evalCp` (`engineLabel()`, virgule ou point selon la langue) ; thèmes et catégories :
  `themeText(theme, champ)` (`src/utils/puzzle.js`) lit `labelEn`/`descriptionEn`/`categoryLabelEn`
  en anglais, le français sinon. Un texte écrit en base
  à la création (titre de la séance sur mesure) l'est dans la langue du joueur, puis ne change plus.
- **Export et calendrier** (lot A3c, 2026-10-17) : la notice du ZIP est écrite dans la langue du
  compte (`translations/export.<langue>.yaml` : `LISEZMOI.txt` en français, `README.txt` en
  anglais), les fichiers de données gardent leurs noms (choix du 2026-10-17) ; le calendrier iCal
  (`IcsWriter`) prend la langue du compte, sinon celle de la requête, sinon l'anglais.
- **Messages de validation** (lot A3b, 2026-10-17), seuls textes d'erreur que le front montre tels
  quels (les 422, `apiErrorMessage`) : ceux des contraintes de Symfony sont traduits par le
  framework dans la langue de la requête ; ceux écrits pour l'application (`message:` d'une
  contrainte, `buildViolation()`) gardent leur texte anglais, qui sert de clé dans
  `translations/validators.fr.yaml` (pas de fichier anglais : la clé s'affiche). Les refus des
  formulaires de l'admin boutique (`App\Shop\Admin\Payload::fail($champ, 'shop.cle', $params)`) sont
  des clés du domaine `admin` (`translations/admin.<langue>.yaml`), traduites par
  `AdminShopController` au moment de répondre. Les autres erreurs ne portent pas de texte pour
  l'utilisateur : le front les nomme d'après leur statut ou leur code (`detail`).
- Tests : `tests/Unit/I18n/UserLocaleTest.php`, `tests/Functional/I18n/RequestLocaleTest.php` ; emails :
  `LoginControllerTest` (langue de la requête, anglais sans langue), `ForgotPasswordControllerTest`
  (langue portée par le message, celle du compte d'abord), `ReminderTest` (compte en français),
  `AccessRequestTest` (langue du visiteur), `InvitationKeyTest` (langue de l'admin).
